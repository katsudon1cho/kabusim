# 1日数回・調査型の仮想運用エージェント

Claude Code が自分でニュースを調べ、判断し、仮想の売買を行い、日報を書く。実際の金銭は動かない。

## 構成

```
Claude Code（判断・調査・執筆）
  ├─ WebSearch / WebFetch  → ニュース収集
  ├─ Bash → broker.py      → 台帳操作。ここで全ルールが強制される
  └─ Write → reports/*.md  → 日報
```

**判断はLLM、ルールの強制はコード**という分離が設計の芯。`broker.py` は判断を一切しない。
検証と記録だけをする。Claude 側が何を出力しても、ユニバース外・レバレッジ・空売り・
集中しすぎ・過剰売買は通らない。

## セットアップ

### Linux / Mac

```bash
pip install yfinance
npm install -g @anthropic-ai/claude-code   # 未導入なら
chmod +x session.sh

python3 broker.py init --us 50000 --jp 20000000
BROKER_OFFLINE=1 python3 broker.py status   # ダミー価格で動作確認
```

`session.sh` は環境変数で挙動を差し替えられる。

| 変数 | 既定 | 用途 |
|---|---|---|
| `PYTHON` | `python3` | broker.py を動かすインタプリタ |
| `MODEL` | `claude-opus-5` | 判断に使うモデル。1年の実験なので正式名で固定している |
| `EFFORT` | `high` | 推論の深さ |
| `MAX_TURNS` | `60` | 暴走時の上限 |

**`MAX_TURNS` で打ち切られると、判断の途中で終わったのに、そこまでの約定は
`state.json` に確定済みという中途半端な状態が残る。** 防ぐ手立てはないので、
打ち切られたことが `journal.jsonl` の記録の先頭に明示されるようにしてある。

プロンプトには**予定時刻・実際の実行時刻・そのときの市場の状態**が入る。
定時実行は数時間ずれることがあり、`jp-open` が12:45に走った実績がある。

    現在 2026-08-06 14:59 JST（木）
      日本市場: 後場（引けまで31分）
      米国市場: 閉場

セッション名は予定であって事実ではないので、`broker.py clock` の結果を渡して
名前ではなく現実に合わせて判断させている。20分以上ずれている場合は
「セッション名が示す市場の状態は当てになりません」と明示する。

なお時刻は Python で出している。環境によっては bash の `date` が `Asia/Tokyo` を
解決できず UTC を返す（Git Bash がそうで9時間ずれる）。

### Windows

`session.sh` は bash / cron 前提なので動かない。`run_session.ps1` を使う。

```powershell
python -m pip install yfinance
npm install -g @anthropic-ai/claude-code

python broker.py init --us 50000 --jp 20000000
$env:BROKER_OFFLINE=1; python broker.py status
```

**`python` と `python3` が別のインタプリタを指す環境が多い。** yfinance を入れたほうと
`run_session.ps1` の `$Python` を必ず一致させること。

同じディレクトリに `CLAUDE.md` `broker.py` と、起動スクリプト（`session.sh` または
`run_session.ps1` + `register_tasks.ps1`）を置く。

## スケジュール（JST）

1日4セッション + 日報1回。

| 時刻 | セッション | 曜日 |
|---|---|---|
| 9:15 | jp-open | 月〜金 |
| 14:45 | jp-close | 月〜金 |
| 23:00 | us-open | 月〜金 |
| 4:15 | us-close | 火〜土 |
| 6:00 | report | 火〜土 |

### GitHub Actions（推奨・PC不要）

`.github/workflows/session.yml` が5本の cron でセッションを回し、`state.json` /
`journal.jsonl` / `equity_log.csv` / `reports/` をリポジトリにコミットして戻す。
手元のPCを起動しておく必要がない。

**必要な準備:**

1. トークンを作る（Pro / Max のサブスクをそのまま使う。API従量課金にはならない）

   ```bash
   claude setup-token
   ```

2. 出力されたトークンをリポジトリの Secrets に `CLAUDE_CODE_OAUTH_TOKEN` として登録

   ```bash
   gh secret set CLAUDE_CODE_OAUTH_TOKEN
   ```

3. 台帳を初期化してコミットしておく（未初期化だとワークフローは即座に失敗する）

**注意点:**

- **トークンの有効期間は1年。** 切れるとセッションが全部落ちるので、期限を控えておく
- **cron は UTC 固定で、しかも混雑時は10〜30分遅れる。** `us-close` を引けの45分前に
  置いてあるのはこのため。夏時間の切り替えはワークフロー冒頭のコメントを参照
- `concurrency` で直列化してあるので、セッションが重なっても `state.json` は壊れない
- 手動実行は Actions タブの「Run workflow」から。セッション種別を選べる

### Linux / Mac（cron・手元で回す場合）

```cron
15  9 * * 1-5  cd ~/trader && ./session.sh jp-open
45 14 * * 1-5  cd ~/trader && ./session.sh jp-close
0  23 * * 1-5  cd ~/trader && ./session.sh us-open
45  4 * * 2-6  cd ~/trader && ./session.sh us-close
0   6 * * 2-6  cd ~/trader && ./session.sh report
```

### Windows（タスクスケジューラ）

```powershell
.\register_tasks.ps1            # 夏時間の時刻で5本登録
.\register_tasks.ps1 -Winter    # 11月の切り替え時にこちらで登録し直す
.\register_tasks.ps1 -Remove    # 全部消す
```

`-WakeToRun` と `-StartWhenAvailable` を付けて登録するので、スリープからは自動復帰し、
逃したセッションは次回起動時に走る。**電源が完全に切れていると実行されない。**
確実にやるならスリープを無効にして常時起動させること。

**米国市場は夏時間で1時間ずれる**（冬は23:30開場→翌6:00引け）。`-Winter` を付けると
us-open 23:45 / us-close 5:45 / report 7:00 で登録し直す。忘れると us-open が開場前、
us-close が引け後に走る。

### 遅延について（重要）

**GitHub の `schedule` はベストエフォートで、実測で最大3時間半ずれた。**
寄り付き後セッションが昼過ぎに走り、引け前セッションが引け後に走る。

時刻の正確さが要るなら、外部の定時実行サービスから `repository_dispatch` を叩く。
受け口は実装・検証済みで、送信から数秒で起動する。手順は **[SCHEDULE.md](SCHEDULE.md)**。

    # 判断セッション
    {"event_type":"session","client_payload":{"session":"jp-open"}}
    # 価格更新
    {"event_type":"prices"}

祝日判定は入れていないので、休場日は Claude が「値が動いていない」と気づいて何もしないはず。

## 消費量の計測

`claude -p --output-format json` の戻り値から、セッション1回ごとに以下を
`usage_log.csv` に記録している。**失敗したセッションの分も記録される**（枠は消費されるため）。

| 列 | 中身 |
|---|---|
| `turns` / `duration_s` | 対話ターン数と所要時間 |
| `input_tokens` / `cache_create` / `cache_read` / `output_tokens` | トークン内訳 |
| `web_search` / `web_fetch` | **実際に何回調べたか** |
| `cost_usd_equiv` | API換算の目安額 |

`cost_usd_equiv` は **API で同じことをした場合の目安**であって、サブスクリプションで
動かしている限り実際の請求額ではない。セッション間で消費を比べるための物差しとして見ること。

消費が重いと分かった場合の調整先は、効果の大きい順に:

1. **モデルを使い分ける** — `session.sh` の `claude` 呼び出しに `--model sonnet` を足す。
   日々のセッションを下げ、日報だけ上位モデルにする構成が現実的
2. **頻度を下げる** — ワークフローの cron を減らす。削るなら寄り付き直後（判断材料が薄い）から
3. **`MAX_TURNS` を絞る** — `web_search` の実績値を見てから決める

**注意: このエージェントはあなた自身の Claude Code と同じ利用枠を使う。** 制限は5時間ごとの
窓で効くので、日中のセッションが枠を食って自分の作業が止まることがありうる。
総量だけでなく、`usage_log.csv` の `ts` 列で時間帯の偏りも見ること。

## スマホから見る（PWA）

`docs/` に、GitHub Pages で配信する閲覧用の単一ページアプリを置いてある。
`build_site.py` が `state.json` / `equity_log.csv` / `journal.jsonl` / `reports/*.md` を読んで
`docs/data/summary.json` を書き出し、それだけを画面が読む。

画面は4つ。

| タブ | 中身 |
|---|---|
| 概要 | ブックごとの総資産、ベンチマーク比較、日次の資産推移 |
| 保有 | 保有銘柄の一覧。タップで個別銘柄へ |
| 日報 | `reports/*.md` を日付で切り替えて読む |
| 履歴 | **却下を含む**全注文と、その理由 |

個別銘柄では **1日（5分足）／1ヶ月／1年** のチャート、現在値と前日比、簿価・損益・比率、
25%上限までの余裕、そして **`journal.jsonl` から引いたその銘柄を買った理由**を表示する。

- 外部CDNを一切読まない。Service Worker で圏外でも直近の内容が読める
- ホーム画面に追加するとアプリのように開く

### 価格の更新

`update_prices.py` が `docs/data/prices.json` を作り、**市場が開いている間だけ15分ごとに**
`.github/workflows/prices.yml` が走って更新する。Claude は起動しないので**利用枠は消費しない**。
画面側は価格データがあればそちらを優先し、総資産とベンチマーク差を計算し直す。

**完全なリアルタイムではない。** yfinance 自体が数分遅れるうえ、GitHub のスケジュール実行が
5〜20分ずれることがあるので、実際の粒度は **15〜30分**。秒単位が必要なら、ブラウザから
直接取得する中継サーバー（Cloudflare Worker など）を別途立てる必要がある。

米国の夏時間・冬時間で cron の時間帯がずれる。`prices.yml` 冒頭のコメントを参照。

### サイトの配信方法

**Pages はブランチではなく GitHub Actions のビルド成果物から配信している。**
価格更新は1日約50回走るため、コミットして配信する方式だと git の履歴が価格データで埋まり、
肝心の「いつ何を判断したか」を追えなくなるため。`docs/data/` は毎回ビルド時に作り直すので
リポジトリには含めていない（`.gitignore`）。

デプロイは `deploy-pages.yml`（再利用ワークフロー）が担い、`session.yml` と `prices.yml` の
両方から呼ばれる。

**有効にする手順:** リポジトリの Settings → Pages で Source を「Deploy from a branch」、
ブランチを `main`、フォルダを `/docs` に設定する。数分後に
`https://<ユーザー名>.github.io/<リポジトリ名>/` で開く。

静的サイトはディレクトリ一覧を取得できないので、日報の索引は `build_site.py` が
生成している。日報を手で足したときは `python build_site.py` を流し直すこと。

アイコンを作り直したいときは `python make_icons.py`。

`journal.jsonl` の却下記録は捨てないこと。Claude が何をやろうとして
止められたかは、エージェントの癖を知る一番の材料になる。

## ガードレール（broker.py 冒頭で変更可）

| 定数 | 既定値 | 意図 |
|---|---|---|
| `MAX_POSITION_PCT` | 25% | 1銘柄への集中を防ぐ |
| `MIN_CASH_PCT` | 2% | フルインベストを防ぐ |
| `MAX_BUYS_PER_DAY` | 買い4件/ブック | **過剰売買の抑制。一番効く制約** |
| `COOLDOWN_HOURS` | 20時間 | 同じ銘柄での往復売買を防ぐ |
| `LOT` | 日本株100株 | 単元株制度 |

**上限は「買い」だけに掛かる。売りに制限は無い。** 売りまで止めると、買いで枠を使い切った日に
損切りができなくなり、CLAUDE.md の「損切りラインを守れ」と矛盾するため。売りの乱発は
クールダウンと保有銘柄数（25%上限で最大4〜5銘柄）が事実上の歯止めになっている。

**ベンチマーク自身（SPY / 1306.T）と QQQ はユニバースに入れていない。** ベンチマークを買えば
その分はベンチと同じ動きになりアルファが出ない。QQQ は中身が個別銘柄と重複するため、
NVDA 25% + QQQ 25% のように25%上限を迂回する抜け穴になる。

**ユニバースは各ブック45銘柄前後。** レバレッジやインバースETFを禁止しているのは
ユニバース制限そのもので、`broker.py` に別途のレバレッジ判定は無い。
**ユニバースを撤廃すると TQQQ などが買えるようになり、「レバレッジ不可」が崩れる。**

銘柄数がこの規模になると全数点検は現実的でないため、CLAUDE.md の手順4で
**決算予定・当日の値動き・保有と同業種**の条件に掛かったものだけを調べさせている。
条件を明示しているのは、「話題になっている銘柄だけを追うと、すでに織り込まれたものばかり
見ることになる」偏りを避けるためと、選び方を記録に残すため。

    python broker.py universe   # 値上がりで買えなくなった銘柄が無いか点検する

日本株は単元100株なので、株価が上がると候補に載ったまま必ず却下される銘柄が静かに増える。
定期的にこれで確認すること。

### 絞り込みと値動きの確認

    python broker.py screen --book jp   # 条件に当てはまる銘柄だけを抽出（約10秒）
    python broker.py history LLY        # 騰落率・52週レンジ・直近10日

`screen` は「当日の値動きが±3%以上」「決算が直前・直後」を**コード側で判定**して、
値動きの大きい順に最大8件返す。45銘柄をモデルに1つずつ調べさせるのは非現実的で、
そうすると結局ニュースに出た銘柄だけを追うことになり、すでに織り込まれたものばかり見る。

`history` を用意したのは、`quote` の現在値だけでは「動いたかどうか」が分からず、
モデルがニュース本文から「〜とみられる」と推測していたため。手元で確認できるようにした。

**日本株は単元100株なので、元本が小さいと値がさ株が構造的に買えない。**
1株の値段が `総資産 × MAX_POSITION_PCT ÷ 100` を超える銘柄は一度も約定しない。
元本2,000万円で1株50,000円が上限。銘柄を足すときは必ずこの計算をすること
（キーエンス 1株約83,000円、東京エレクトロン 約57,000円などは対象外になる）。

## 設計上の割り切り

- **データは15〜20分遅延**（yfinance）。1日数回の判断なら実害はほぼ無い
- **2ブック分離**で為替を排除。混ぜると成績がドル円由来か銘柄選択由来か分からなくなる
- **配当を無視**している。**ただし影響の向きは2つのブックで逆になる**
  - 米国株: SPY（約1.2%）> メガキャップテック（約0.5%）なので**ベンチマークが過小評価**。
    勝っていても実際はトントンの可能性がある
  - 日本株: 三菱UFJ・三菱商事・KDDI・JT などは3〜4%で 1306.T（約2%）を上回るので、
    **自分のブックのほうが過小評価**。高配当銘柄を持つほど記録上は年1〜2pt不利に出る
  - どちらも数ptの差は誤差として読むこと
- **税金・信用取引・空売りなし**
- **自動の逆指値（ストップロス注文）は無い。** 損切りは Claude がセッション中に自分で判断して
  売る。セッション間に暴落しても、次の起動まで何も起きない
- **元本は US $50,000 / JP ¥20,000,000。** 日本株を大きくしてあるのは単元100株の制約で、
  同額だと買える銘柄が構造的に狭まるため。2ブックは独立評価なので金額の違いは比較に影響しない

## 読み方についての注意

数ヶ月勝っても、それは実力ではなく分散を捨てた結果のブレかもしれない。
評価するときは累積リターンだけでなく、`equity_log.csv` から最大ドローダウンと
リターンのばらつきも見ること。ベンチマークより値動きが荒いだけなら、
上昇相場で勝つのは当たり前で、下落相場では同じ幅だけ負ける。

この実験で一番価値があるのは成績表ではなく、`journal.jsonl` と `reports/` に残る
**「なぜそう判断したか」の記録**。数ヶ月後にそれを読み返すと、
当たった理由と外れた理由がはっきり分かる。

## 次の一手（実運用が回り始めたら）

- **米国株を Alpaca Paper Trading に置き換える。** 無料でリアルタイム気配値に対する
  約定シミュレーションが得られるので、この自前シミュレータより精度が高い
- **同じ CLAUDE.md を別モデルで並走させる。** 単独の成績には意味がないが、
  条件を揃えた比較なら情報量がある
- **ベンチマークを等ウェイト版（RSP）に変える。** 大型株偏重の影響を切り分けられる
